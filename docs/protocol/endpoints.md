# Endpoints: every request the project has seen or uses

Status: 2026-10-24, the lab rule (**lab accounts contact only each other; everything else is allowed**), written for
it by Task 7 of `docs/plans/20261023-lab-fence-contacting-writes-only.md` and checked against every endpoint M2 touched
(its Task 28: the native reads, plain requests and writes in `teams-proto`, `teams-auth`'s, the sign-in windows' and
`proto-lab`'s probes); the rows themselves date from M0 to M2. One
row per endpoint the lab has seen the web client send, a lab command sent itself, the native client sends, or the
bundle names and a note relies on. The notes in this directory explain the endpoints; this file only lists them, so
that "which endpoints do we know, and what happens to each" has one answer. Built from the protocol notes, the code
(`teams_fence::contacting`, which the browser fence and the native transport share; `proto-lab`'s frame rule and
expected-deny list; `teams-proto`'s reads, requests, writes and frames, `teams-trouter`, `teams-auth`) and a local
count of the captures under the lab's data dir (method, host and path pattern only, ids normalised; nothing of a
capture is copied here).

**Kept current by every task that touches an endpoint.** A task that captures, maps, carves out, expects or uses a new
endpoint, or changes how one is treated, adds or updates its row here in the same change. To add a row: put it in its
service's table; write the path with placeholders only (`<region>`, `<partition>`, `<chat>`, `<message>`, `<mri>`,
`<guid>`, `<id>`, `<n>`), never a real id, host number, site or tenant name; describe it in our own words; fill the
two treatment columns from the code as it stands; link the note that describes it and name the task; say where the
evidence comes from. An endpoint first seen in a capture and not yet reviewed goes in as **seen, not reviewed**, and
keeps that until a note describes it.

## How to read a row

- **Path** is relative to the section's host or base; `?a&b` lists the query parameters that matter (names only).
- **Contacting?** is what `teams_fence::contacting` makes of the request
  ([fence-targets.md](fence-targets.md#the-contacting-services)), the same in the lab browser and in the native
  transport:
  - `no`: it reaches nobody and is let through: every `GET`, `HEAD` and `OPTIONS` with no body and no method override
    (a read, unlogged), every request to a host that is no contacting service, and a mutating request on the
    middle tier (a contacting service) whose path its rule doesn't count as contacting: no team, chat, meeting or
    other people segment (mutating ones logged to `fence.log` as `allowed`, by method, host and path shape);
  - `mapped: <WriteKind>`: a write the table maps to a target, let through only with a permit from `Fence::check`: an
    existing target after a fresh member read, a new one (`Scope::New`: a chat's creation, the test call's start) by
    its proposed participants, with no member read, an operation on a call (`Scope::CallOperation`) by the lab's call
    rule: a join by the chat it names (read fresh), an answer or a decline only of the account's own offered
    invitation (its group chat read fresh), an `add` by its invitees, and any other operation (what a call sends once
    it was let in) permitted with no member read and no lookup, logged;
  - `carve-out`: a mutating request on a contacting service that a named row lets through as reaching nobody
    (typing, read receipts, the account's own view, feed, settings, endpoints and token exchanges, reads sent as a
    `POST`), logged `allowed`;
  - `yes: <service>`: a mutating request on a contacting service that no row maps or carves out (`Unreadable`):
    denied. When a writing scenario meets it without needing it, the cell names its class on the reviewed
    expected-deny list (`crates/proto-lab/src/scenario/expected.rs`), which keeps it denied but doesn't fail the run;
  - `forced deny` is added where a scenario denies the request on purpose before it is classified (its probe,
    `ab-image`'s and `ab-file`'s media and file writes, a research run's held-back request).

  A frame on a WebSocket is judged by the browser fence's frame rule (`proto_lab::fence_ws::classify_frame`): on a
  Trouter socket socket.io types `0`, `1`, `2`, `3` (the answer to a delivery, a call's receipts and acknowledgements
  among them) and `5` pass and every other frame is denied; every frame on a contacting service's socket is denied;
  frames on any other socket pass.
- **Native** is what the native client does with it (`crates/teams-proto`, `crates/teams-auth`): `Read` (a `GET`),
  `Request` (a plain request through `Transport::send`: sent only when `contacting` calls it `no` or `carve-out`,
  logged `allowed` when mutating, refused before anything is sent otherwise), `Authorized<Mutating>` (a sealed write
  sent only with its permit), `OwnFrame` (a typed frame through `teams-trouter`'s `FrameSink`, never logged:
  a frame isn't a contacting write), `teams-auth` (its own HTTP client, not the transport), `teams-signin` (the
  sign-in window's guard), `teams-trouter` (the push socket, its own WSS connection to the Trouter hosts only), **not
  used** (its host is one of the transport's services, the chat service at `v1`, the registrar, Trouter's HTTP side,
  the middle tier's `/api/mt/…` base, Graph's `v1.0`, CSA and UPS, so a `Read` or a `Request` could name it, judged
  as above; none does yet), or **no service** (its host is none of those, so the transport can't send it at all; a
  new service is a code change). The personal build keeps sealed lists beside these (`OwnState`, `PostRead`, sent by
  `HttpTransport::own_state` and `::post_read`); a lab binary sends their entries as `Request`s. The personal build
  (`crates/teams`, M2 T27) sends no `Request` at all: the registration goes as its `OwnState` entry, the profile
  lookup and the presence read only through `Client::lookup` under a `Fence::check_post_read_among` permit naming the
  account or people of its stored chats; it adds no endpoint of its own.
- **Notes · task**: the note that describes it, and the task that captured, mapped or built it (M0, M1 or M2 task
  number).
- **Evidence**: `seen` (in the lab's captures, with the scenarios), `probe` (a `proto-lab` command's own live request),
  `native` (the native client's own live request: `teams-headless`, M1 Tasks 19 and 21, and later), `bundle only`
  (named in the web bundle `26260.1717.5229.7049`, never on the wire), or `seen, not reviewed` (in the captures,
  described nowhere but here).

## Chat service (`https://<teams origin>/api/chatsvc/<region>/`)

The base is authz's `chatServiceAfd` GTM; `<teams origin>` is `teams.microsoft.com` or `teams.cloud.microsoft`, and the
lab's region is `amer`. The regional form `https://<region>.ng.msg.teams.microsoft.com/` (paths from `v1/` on) was
seen only in answers (`chatService` GTM, `Location` headers); the classifier's mapped writes, the fence's member read
and the transport accept both ([fence-targets.md](fence-targets.md#the-chat-service)). Ids are one percent-encoded
segment. The chat service is a contacting service: a mutating request on it that no row below maps or carves out is
denied.
